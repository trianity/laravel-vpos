# Prompt 04 — Complete the hosted card payment lifecycle

Work in `trianity/laravel-vpos` after Prompt 03. Use [docs/README.md](README.md), Basic Methods, the payment lifecycle, request signing, and the basic, extended and OneClick-template PHP JSON fixtures.

1. Implement or correct `POST payment/init`, signed `GET payment/process/{merchantId}/{payId}/{dttm}/{signature}`, `GET payment/status/{merchantId}/{payId}/{dttm}/{signature}`, and `PUT payment/close`, `payment/reverse` and `payment/refund` through the shared stack. Keep the legacy adapter aligned as its operations are migrated. Fix response action handling where it is already needed by the card lifecycle and coordinate concrete 3DS action hydration with Prompt 05.
2. Test standard init, extended metadata and `payOperation=oneclickPayment` with signed fixtures. Keep an integer amount in hundredths on the wire. Enforce the documented HUF whole-forint restriction, allow the supported EUR/USD precision, reconcile totals with cart line totals, preserve numeric order references as strings and cover optional TTL, language and Boolean `closePayment`. Verify omission and signing order. Record any additional documented variant such as payment by link separately with its support status.
3. Provide a signed process URL that the host can hand to the payer's browser. For the sample-compatible method that reads the bank response, use a single GET with redirect following disabled using HTTP client options. Assert the documented 303 and validated Location, and test missing/invalid Location and nonredirect responses. Encode pay IDs with `@` and Base64 characters such as `+`, `/` and `=` once per path segment. Preserve the distinction between generating the URL and consuming the bank's redirect.
4. Test status, full or lower-amount close, reverse, full and partial refund, and authenticated bank business errors. Use the exact optional names `totalAmount` for close and `amount` for refund. Validate what the package can know from the request and leave order balances and gateway state transitions with their owners. A timeout on a mutating call has an unknown outcome. Preserve identifiers for reconciliation and document status checks and operator review before retrying.
5. Implement a typed package-level verifier for documented browser return parameters from GET and form POST. Test valid, tampered, malformed and mismatched returns, optional fields including `authCode`, `merchantData` and `statusDetail`, and status reconciliation when the browser never returns. Require the host to correlate `payId` and order identity, and use the verified bank status and the host's idempotent state transition for fulfillment.

Acceptance criteria: all card operations have signed wire and failure tests, the hosted handoff works through a browser-facing URL, and return verification and payment confirmation are separate, testable operations.
