# Prompt 05 — Complete OneClick, wallet and 3DS wire parity

Work in `trianity/vpos` after Prompt 04. Use [docs/README.md](README.md), the matching PHP fixtures and methods, and the K&H OneClick, Apple Pay, Google Pay and extension pages.

1. Cover all nine POST operations `{oneclick,applepay,googlepay}/{echo,init,process}` through the shared signed client. Verify the OneClick template relationship via `origPayId` and distinguish it from the new `payId`. Test active and unavailable templates and the documented customer-initiated versus merchant-initiated fields and fingerprint rules. Preserve wallet payload encoding, typed nested echo parameters, optional purchase metadata, `sdkUsed`, and provider-specific fields. Enforce each provider's documented conditional fingerprint rules.
2. Replace incomplete or ambiguous 3DS hydration with explicit, PSR-4 types for `actions.fingerprint.browserInit/sdkInit`, `actions.authenticate.browserChallenge/sdkChallenge`, and request `fingerprint.browser/sdk` where documented. Cover `Endpoint` URL, method and `vars`, and verify exact canonicalization against documented examples or cross-checked samples. The package exposes validated action data to the browser or mobile host. Test frictionless, fingerprint, challenge, optional fields and malformed action cases through init, process and status. Fix the existing invalid dynamic dereference in `PaymentResponse::toSign()` if it has not already been removed.
3. Implement and test the extensions in scope for the PHP samples, including the OneClick masked card extension. Check its exact identifier, field order and placement against the pinned sources. Inventory `trxDates` and simple-payment extension variants from the wiki and other language samples. Test supported or already exposed variants and explicitly mark any remaining specification-only support gap. Verify known extension signatures separately with the bank key, outside the parent signature. Define how unknown extensions are handled. Never surface an unknown or invalid extension as verified, and keep masked data out of logs.
4. Use distinct offline fixtures for each provider and phase. Assert exact method, path, payload shape, canonical string, verified result, actionable failure handling, and explicit coverage of independent extension-signature tampering. Never commit live wallet tokens.

Acceptance criteria: the nine sample operations and their supported action variants are covered by deterministic tests, and the matrix distinguishes verified wire behavior from merchant provisioning, real wallet UI and mobile SDK execution.
